# ロードマップ・検証計画

- 更新日: 2026-11-19
- 状態: **開発の優先順案**。実装順は検証結果で調整する。
- 最優先成果物: **外部の既存脆弱性データを使った、閲覧・検索可能な統合Webダッシュボード**
- 方針: 追加API従量課金0円を目標、既存OSS無改造、少数サービスで稼働

## 横断方針: モジュラーアーキテクチャ

**Ansible・Vuls・OpenVASを共通APIで扱えること**を設計要件に追加。データ取得の深さや検査機能の差はCapability、AssetObservation、VulnerabilityFindingによって表す。収集元以外の脆弱性ソース・SNS・Matcher・Scorer・LLM・公開先も交換可能な境界を設ける。

初期からすべてのアダプターを実装せず、**契約と模擬アダプターを先に作り、実装は必要なものから**。モジュラーモノリス＋独立ワーカーを原則とする。詳細は[モジュール化設計](modularity.md)。

## Phase 0: 調査・PoC（実装前）

### P0-1 Vulnerability-LookupのAPI検証

- [ ] 公開APIでCVEの検索・詳細・別名・ソース情報を取得
- [ ] KEV、EPSS、Sightings等の取得仕様・可用性・欠損率を確認
- [ ] 絞込/ページング/差分取得/最終更新情報とレート制限を確認
- [ ] 無料利用・キャッシュ・派生データの公開条件を確認
- [ ] VulnMCPで取得できるツール/必要な認証/更新頻度を調査
- [ ] 自前運用に切り替えた場合の依存サービスと実測CPU/RAM/容量を整理

**受入条件:** 仮の独自APIが、上流の実データからCVE検索/詳細/KEV/EPSS/言及有無を返せる見通しが立つ。採用不可なら理由と代替案を記録。

### P0-2 AI実行方式の検証（独立PoC）

- [ ] 利用中サブスクリプションの正規クライアントから自作MCPを接続できるか
- [ ] 定期実行時にMCP readを利用できるか
- [ ] MCP writeで分析結果を保存できるか（認証/権限/ログも検証）
- [ ] 外部異常検知で追加実行を起動できるか。できなければキューで代替
- [ ] 実行制限・利用規約を確認し、API代用や無断自動化にならないようにする

**受入条件:** 少なくとも「分析待ち取得→要約/予測→書き戻し」の正当なワークフローか、実現できない制約が明確になる。

### P0-3 UIキットの短期比較

- [ ] Tabler / AdminLTE / CoreUIを小画面とデータ密度の観点で比較
- [ ] 標準テーブル、検索、タグ、チャート、ダーク/ライト切替を評価
- [ ] OSSライセンスと追加ビルド工程を調査

**受入条件:** 見た目と保守性の両面で採用キットを一つに絞る。

### P0-4 共通収集契約のPoC

- [ ] AssetObservation / VulnerabilityFinding / CapabilitySet / JobStatus の最小データ契約を定義する
- [ ] Ansible/軽量JSONとVuls/OpenVAS模擬結果を**同じImport/Job API**へ変換できるか検証
- [ ] 結果の一部欠損・取得失敗・同一CVE重複を正しく扱う
- [ ] 上位Web/REST/MCPにスキャナー固有の差異が漏れないことを確認

## Phase 1: 動くダッシュボード（最優先）

- [ ] 既存OSSの公開APIを抽象化する上流アダプター
- [ ] 中間APIの最小構成（検索、詳細、サマリー）
- [ ] 一覧・絞込・詳細ビュー
- [ ] グローバル脅威サマリーと更新時刻/取得失敗の表示
- [ ] My Environment側の領域を設け、案件対応管理は後段で接続
- [ ] REST APIの最小OpenAPIスキーマ
- [ ] 低負荷でのキャッシュ・タイムアウト・API失敗時の表示

**受入条件:** LLMなしで、実際の脆弱性情報を検索し、根拠と更新時刻を見られる。上流障害でもUIが壊れず原因を表示。

## Phase 2: SNS/非公式情報と注目度

- [ ] まず無料・正規経路のSNS/ブログ/GitHubアダプターを実装
- [ ] Xの無料/低コストで適法な取得経路を独立して比較
- [ ] CVE未採番 `ThreatEvent` と証跡データを実装
- [ ] 言及数・増加率・独立した情報源数を時系列集計
- [ ] 誤情報・転載増幅・収集停止の扱いを実装
- [ ] 急浮上候補/悪用確認/未確認の区別をUIへ反映

**受入条件:** 出典を追跡でき、未確認の話題がCVEなしでも表示できる。SNSワーカーが停止しても既存データ閲覧が可能。

## Phase 3: LLM分析・将来予測

- [ ] 分析待ちキュー（優先度/冪等/再実行/失敗状態）
- [ ] 日次1回の分析ワークフロー
- [ ] 異常検知時の追加分析要求（即時起動できなければキューへ）
- [ ] MCPでの読み取り・分析結果書込を認証付きで公開
- [ ] 24時間 / **7日** / 30日の予測・根拠・不確実性を保存
- [ ] 予測時点のスナップショットと後日結果比較
- [ ] LLM停止時も非LLM評価と画面が継続することを確認

**受入条件:** 有料従量課金なしで、実行可能な条件下の日次バッチが成立する。難しい場合も手動実行で同じ処理ができる。

## Phase 4: 案件プロファイル・エージェントレス資産収集

- [ ] プロファイル CRUD と案件別/横断ビュー
- [ ] 資産/ソフトウェア/バージョンの手動登録
- [ ] 資産×脆弱性の候補照合と根拠
- [ ] 案件別の影響判断/対応履歴（対処済み・対象外の抑制を含む）
- [ ] Linux/Windowsの踏み台収集スクリプト（読み取り専用）
- [ ] JSONスキーマ・バリデーション・手動取込
- [ ] HTTPS自動アップロード（認証・再送・ログ）
- [ ] 閉域網収集・手動持込の動作確認

**受入条件:** 2件以上の案件で同一CVEの対応状態が異なっても、互いに干渉しない。JSONを再投入しても資産が不必要に重複しない。

## Phase 5: 外部公開・連携・運用整備

- [ ] 公開REST API / 読み取り専用MCPの範囲とアクセス制御
- [ ] 取得量・ログ・メンテナンスの最小運用設計
- [ ] 外部API→自前Vulnerability-Lookupへの移行テスト
- [ ] 重大イベント時のメール/Discord通知
- [ ] 日次ダイジェスト/レポート
- [ ] 将来はネットワーク機器収集、Vuls等の検査結果取込、NetBox/Zabbix連携

**受入条件:** 公開利用者から内部案件データが参照できず、通知/レポートが正確な出典とステータスを含む。

## 判断を保留している項目

| 項目 | 調査で決めるポイント |
| --- | --- |
| OSSバックエンド | Vulnerability-Lookup第一候補。OpenCTIはCTIグラフ要件が増えた場合の再評価先 |
| 本番用の計算資源 | 既存自宅環境/VPSから、稼働リソースを実測して判断 |
| UI実装技術 | Bootstrapキットとの相性・保守負荷を優先 |
| 中間API/拡張DB | Python FastAPI/PostgreSQL等を候補としてPoC後に決定 |
| SNS/X取得 | 許諾・料金・取得成功率・追跡対象を確認。Playwright採否はサイト別 |
| LLM自動実行 | ChatGPT/Claudeの正規スケジューラ + MCPが成立する範囲を実証 |
| 異常検知スコア | まず解釈可能な規則で実装し、誤検知/見逃しから調整 |
| 保持期間 | 元データの権利/ストレージ/検索用途を踏まえて決める |
| ライセンス | 上流AGPL/CE-EE/データ再配布条件と本プロジェクトのOSSライセンス整合 |
| 正規化精度 | LinuxバックポートとWindows累積更新の判定方法 |
| API公開ポリシー | 小規模共有前提の認証・レート制限・公開フィールド |

## 設計・実装の避けたい方向

- 最初からOpenCTI級のCTI分析・SIEM/CMDB一式を実装する
- 外部従量課金に依存するLLM/ソーシャル収集を中核に据える
- 上流OSSを大幅にfork/改造してアップデートを困難にする
- CVE番号以外で識別できない設計にする
- SNSのバズを確定した脅威や悪用と同一視する
- ユーザーに見せる全操作でLLM推論を実行する
- ダッシュボードより先に通知や複雑な管理機能を作り込む
